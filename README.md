# Conversation Analyzer

Turns a Telegram Desktop JSON export into communication statistics and
evidence-backed insights.

The product loop is deliberately narrow: **import → understand → analyze →
explain → show evidence → summarize.** Statistics are computed exactly, on the
user's device. The AI describes patterns in the conversation and is never
allowed to assess the people in it.

Text-only MVP. Media is recognised, counted and left unanalysed.

---

## Running it

```bash
npm install
cp .env.example .env.local     # add your ANTHROPIC_API_KEY
npm run dev                    # http://localhost:3000
```

`ANTHROPIC_API_KEY` is the only required variable. It is read server-side only;
nothing under `src/lib/ai/` is ever imported into a client bundle.

```bash
npm run verify     # typecheck + lint + unit tests + production build
npm run test       # unit tests (vitest)
npm run test:e2e   # end-to-end (playwright, needs a build first)
npm run fixture    # regenerate the synthetic test conversation
```

To try it without exporting anything from Telegram, upload
`fixtures/telegram-sample.json` — a synthetic eight-month conversation between
two invented people, generated by `scripts/generate-fixture.ts`.

## Where the data goes

This is the part worth being precise about.

| Stage | Runs where | Sees what |
|---|---|---|
| Parsing the export | Browser (web worker) | The whole file |
| Every statistic in the Stats tab | Browser (web worker) | Every message |
| AI analysis | Server → Anthropic | A statistics digest + selected excerpts |
| PDF report | Server (pdfkit) | Aggregates only, no message text |

The export file itself is never uploaded. Before anything leaves the browser,
participants are pseudonymised: Claude sees `Participant A` and `Participant B`,
and the UI substitutes the real display names back in when rendering
(`humanise()` in `src/lib/pipeline/payload.ts`). Message *text* is sent as
written, so names written inside messages are included — the consent screen
says so rather than claiming otherwise.

Nothing is persisted. There is no database, no account, and no shareable URL:
results live in the browser tab until it is closed. Sharing means the PDF, the
Web Share API, or a copied text summary.

The server logs the shape of a run (message counts, call counts, token usage)
and never message content or credentials — see `src/lib/logger.ts`, which
scrubs anything key-shaped and caps value length.

## Architecture

```
Telegram export
   ↓  src/lib/telegram/parser.ts          robust, never assumes a field exists
normalized messages                        src/lib/model/message.ts
   ↓  src/lib/stats/                      exact arithmetic, no model involved
local statistics
   ↓  src/lib/analysis/segmentation.ts    conversation boundaries
segments
   ↓  src/lib/pipeline/excerpts.ts        what is worth sending, and no more
excerpts + statistics digest
   ↓  POST /api/analyze                   server-side key, Zod-validated input
   ↓  src/lib/pipeline/strategy.ts        single pass, or map/reduce over chunks
   ↓  src/lib/ai/claude.ts                structured output + repair retry
structured analysis
   ↓  validation + evidence pruning       src/lib/ai/schema.ts
   ↓  src/lib/client/insights.ts          flashcard deck
UI
```

Everything above the API boundary runs in a web worker
(`src/workers/import.worker.ts`), with a main-thread fallback, so a 50 MB
export does not freeze the tab.

### Provider abstraction

The pipeline depends on `AIAnalysisService` (`src/lib/ai/types.ts`), not on
Anthropic:

```ts
interface AIAnalysisService {
  analyzeConversation(excerpts, context): Promise<Analysis>;         // single pass
  analyzeCommunicationPatterns(excerpts, context): Promise<ChunkFindings>; // map
  generateFinalSummary(findings, context): Promise<Analysis>;        // reduce
  usage(): UsageTotals;
}
```

`ClaudeAnalysisService` is the one implementation. Adding another provider is a
new class; nothing else changes.

### Media

No media is analysed, and none is sent anywhere. `MediaProcessor`
(`src/lib/media/types.ts`) already defines `processImage` / `processAudio` /
`processVideo`, and `MessageType` already covers `IMAGE`, `AUDIO`, `VIDEO`,
`STICKER` and `REACTION`, so adding a processor later does not reshape the
conversation model. Today the registry holds `UnsupportedMediaProcessor`, which
produces the placeholder shown in the UI.

## How the statistics are defined

Where a statistic depends on a judgement call, the rule is stated next to the
number in the UI and in the PDF. The two that matter:

**Conversation boundaries.** A message starts a new conversation when more than
`ANALYSIS_CONVERSATION_GAP_MINUTES` of silence preceded it (default 6 hours,
adjustable in the preview screen). This is a proxy: a reply sent seven hours
later is still a reply, and two unrelated topics five minutes apart are still
one segment here.

**Initiation.** Whoever sent the first message of a segment. Inherits every
limitation of the boundary rule.

**Response time.** The gap between the last message of one person and the first
reply from the other, measured only *inside* a segment. A gap that crosses a
boundary is a conversation break, not a slow reply, and is excluded — which is
why the longest silence is reported separately from the longest reply.

**Time of day / weekday.** Taken from the exporter's own wall clock. Telegram
gives both a naive local timestamp and `date_unixtime`; the parser derives the
export's UTC offset by comparing them, keeps the absolute instant for duration
maths and the wall clock for "what hour was this". Exports without
`date_unixtime` are read as written, and the UI says so.

**Words.** Tokenised across alphabets, apostrophes normalised so `i'll` matches
the stopword list, English and Russian filler removed, pure numbers dropped.
Phrases are bigrams taken from the raw token stream, so removing stopwords can
never glue together words that were not adjacent.

Raw inputs stay available to the caller, so any of these can be improved later
without re-parsing.

## Large conversations

`chooseStrategy()` picks the approach from the conversation's size:

- **Single pass** when the conversation is at or below
  `ANALYSIS_SINGLE_PASS_MAX_MESSAGES` (default 800) *and* the selected excerpts
  fit inside `ANALYSIS_EXCERPT_CHAR_BUDGET` (default 45 000 characters). One
  request, and the model sees everything at once.
- **Chunked** otherwise: excerpts are packed into chronological periods under
  the per-call budget (capped at `ANALYSIS_MAX_CHUNKS`, default 8), each period
  is analysed on its own, and a final pass synthesises those findings against
  the complete statistics.

Deterministic statistics always cover every message, whichever path runs.

Cost control is the same mechanism: nothing is recomputed by the model, no raw
JSON is ever sent, excerpts are budgeted and truncated, and model, effort and
token settings are configuration rather than constants. Per-chunk passes run at
`ANTHROPIC_EFFORT` (default `medium`); the final synthesis runs at
`ANTHROPIC_EFFORT_SYNTHESIS` (default `high`).

## What the AI is asked to do

`src/lib/ai/prompts.ts` holds the system prompts. Two rules drive them:

1. **Analyse the conversation, not the people.** Trait, diagnosis and verdict
   language is ruled out explicitly. The output schema enforces the split: every
   pattern has a separate `observation` (what is literally there),
   `interpretation` (one reading among several) and `uncertainty` (what this
   cannot establish). The UI renders those three as separate labelled blocks so
   interpretation is never mistaken for fact.
2. **Never recompute.** The statistics arrive as finished figures.

Output is forced through a Zod schema (`analysisSchema`) via structured
outputs. Model output is treated as untrusted throughout:

- a response that fails validation triggers one repair attempt with the
  validation error fed back, then fails cleanly as `AI_INVALID_RESPONSE`;
- if structured output does not bind, JSON is recovered from the response text
  and validated anyway;
- `stop_reason: "refusal"` and `max_tokens` are handled distinctly;
- evidence citing message ids that were never sent is dropped before rendering
  (`sanitiseAnalysis`);
- the client re-validates the analysis a second time before it reaches the UI.

Evidence quotes are rendered from the messages held locally, looked up by id —
not from text the model echoed back — so an excerpt shown in the evidence
drawer is always something that was really in the export.

## Errors

Every failure that can reach a user goes through `AppError`
(`src/lib/errors.ts`), which carries a stable code, a human-readable message, a
concrete next step, and whether retrying is worth it. Stack traces, provider
payloads and API keys never cross that boundary. Covered: invalid JSON,
unsupported export, empty conversation, single participant, oversized file,
malformed request, missing configuration, provider timeout / rate limit /
outage / refusal / malformed response, network failure, and PDF generation
failure (which falls back to the browser's print dialog).

## Configuration

All of it is documented in `.env.example` and read once in
`src/lib/config.ts`. Nothing expensive is hard-coded anywhere else.

| Variable | Default | What it does |
|---|---|---|
| `ANTHROPIC_API_KEY` | — | Required. Server-side only. |
| `ANTHROPIC_MODEL` | `claude-opus-5` | Model for every analysis call. |
| `ANTHROPIC_MAX_OUTPUT_TOKENS` | `8000` | Output ceiling per call. |
| `ANTHROPIC_EFFORT` | `medium` | Effort for per-chunk passes. |
| `ANTHROPIC_EFFORT_SYNTHESIS` | `high` | Effort for single-pass and synthesis. |
| `ANTHROPIC_TIMEOUT_MS` | `120000` | Per-request timeout. |
| `ANTHROPIC_MAX_RETRIES` | `2` | SDK retries for transient failures. |
| `ANALYSIS_SINGLE_PASS_MAX_MESSAGES` | `800` | Single-pass / chunked threshold. |
| `ANALYSIS_EXCERPT_CHAR_BUDGET` | `45000` | Excerpt characters per call. |
| `ANALYSIS_MAX_CHUNKS` | `8` | Ceiling on map-phase calls. |
| `ANALYSIS_CONVERSATION_GAP_MINUTES` | `360` | Conversation boundary. |
| `NEXT_PUBLIC_MAX_UPLOAD_MB` | `100` | Largest accepted export. |
| `MAX_ANALYZE_REQUEST_MB` | `8` | Largest accepted analyze request. |
| `RATE_LIMIT_MAX_REQUESTS` / `RATE_LIMIT_WINDOW_MINUTES` | `10` / `10` | Per-caller limit on `/api/analyze`. |
| `ANALYZER_DEBUG` | `0` | Extra (content-free) pipeline logging. |

## Stack

Next.js 16 (App Router) · React 19 · TypeScript (strict, `noUncheckedIndexedAccess`)
· Tailwind CSS v4 · Zod · Recharts · pdfkit · Vitest · Playwright.

No database — none is needed for the MVP, and adding one would mean storing
conversations the product deliberately does not keep. No authentication,
payments, Telegram OAuth or admin surface: none of them are required for the
loop above.

The PDF is rendered server-side with pdfkit rather than printed from the
browser, so the output is a typeset document. DejaVu Sans is embedded
(`assets/fonts/`, license included) because the PDF standard-14 fonts cannot
render Cyrillic, and Telegram exports frequently are not Latin-only.

Typography uses the system font stack: no webfont request, no layout shift, and
it reads well on every platform.

### Charts

Four colours, validated for colour-vision-deficiency separation, assigned in a
fixed order so a participant keeps one colour everywhere — charts, comparison
bars, badges, evidence and the PDF. Colour is never the only cue: every series
carries a visible label, and each chart has a "View as table" fallback. One
y-axis per chart, recessive grid lines, and no animation, so a chart is
readable the instant it appears.

## Tests

`npm run test` — 102 unit tests over the parser (text entity flattening,
timezone derivation, media classification, malformed and unsupported exports,
full-account exports), the statistics engine (hand-checkable numbers for
initiation, response times, characteristics, time bins and words), the AI layer
(schema violations, repair retry, JSON recovery, refusals, provider error
mapping, evidence pruning), the pipeline (excerpt budgets, pseudonymisation,
strategy thresholds, chunked orchestration, progress events), the PDF (schema,
Cyrillic rendering, empty series), errors and the redacting logger.

`npm run test:e2e` — 7 Playwright scenarios on desktop and mobile viewports,
against a real production build: landing → upload → parse → preview → gap
adjustment → consent → progress → insight cards → keyboard navigation →
evidence drawer → stats → **a real server-rendered PDF download**. Only the
Anthropic call is stubbed; the test also asserts that the outgoing request
contains no real participant names. An invalid file is checked for a readable,
internals-free error.

If the environment ships its own Chromium, point Playwright at it:

```bash
PLAYWRIGHT_CHROMIUM_PATH=/path/to/chromium npm run test:e2e
```

Semantic HTML, one visible focus style everywhere, a skip link, labelled form
controls, a focus-trapped consent dialog with Escape to close, the card deck as
